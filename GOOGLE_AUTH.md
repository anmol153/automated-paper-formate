# Google sign-in

Google sign-in is implemented alongside email/password login. It uses the official
Google Identity Services button, the existing `google-auth` Python dependency, and
the application's revocable HttpOnly-cookie/CSRF session system. No dependencies
were installed or added. Google authentication does not replace conference roles,
grant paper access or authorize Google Drive imports.

The approved local activation is complete: the backend selects
`backend/data/platform-v8.db`, and the web OAuth client ID is configured. Phase 9
retains the schema-7 database and a configuration backup; see [PHASE9.md](PHASE9.md).
The backend
and frontend proxy both report Google sign-in enabled. The original `platform-v4.db`
and verified backups are retained. An end-user Google consent flow has not yet been
exercised, and no production deployment was performed.

## Google project setup

1. In Google Auth Platform, configure the app's branding and audience, and create an
   OAuth client with application type **Web application**.
2. Add the frontend's exact scheme/host/port to Authorized JavaScript origins. For
   local development, Google documents registering `http://localhost` and the actual
   port origin, such as `http://localhost:5173`. Register your deployed HTTPS origin
   separately.
3. Configure applicable test users while the Google app is in testing. Authentication
   needs only the standard OpenID/email/profile information; no Drive scope is needed.
4. This implementation uses the popup JavaScript callback, so it does not need a
   backend redirect URI or client secret. Do not configure `/auth/google/complete`
   as an OAuth redirect: it is the app's JSON credential-verification API.

See [Google's web-client setup instructions](https://developers.google.com/identity/gsi/web/guides/get-google-api-clientid).

Set the public client ID in `backend/.env`, after activation is approved:

```dotenv
GOOGLE_OAUTH_CLIENT_ID=YOUR_WEB_CLIENT_ID.apps.googleusercontent.com
```

Use the complete client ID generated by Google. The placeholder above is not usable.
The example configuration also documents this setting. Compose accepts the same
variable from its invoking environment. Do not substitute `GOOGLE_API_KEY`, a service
account identifier, an ID token, or a client secret. The frontend obtains the client
ID from the backend configuration endpoint; no frontend rebuild with secrets is needed.

Keep the current persistent `SECRET_KEY`. For plain HTTP local development use
`COOKIE_SECURE=false`; use HTTPS and `COOKIE_SECURE=true` in production. Serve browser
API calls through the existing same-origin Vite/Nginx proxy so the browser can send
its session cookies and read the separate CSRF cookie. Existing CORS origins must
also include the actual frontend origin. Avoid mixing `localhost` and `127.0.0.1`
within a browser session.

## User experience

The login/registration screen has a Google sign-in section. When enabled it loads
Google's official button and opens the account chooser on user interaction. One Tap,
automatic account selection and automatic sign-in are not enabled. A new eligible
Google user receives an ordinary Paper-Format account with no conference memberships.
Returning users are matched by their stable Google subject, preserving the same
Paper-Format user ID, papers and memberships even if Google's email changes.

Existing password users sign in normally, open **Account**, enter their current
Paper-Format password, then choose the Google account to connect. The session and
Google account must both be confirmed. The connected Google email can differ from
the app account email; that explicit connection does not rename or merge either
account. Future Google logins use the existing app account. Password login remains
available for those existing password accounts.

The app never automatically merges password accounts by Google email, including
case-insensitive email collisions. It instructs the user to sign in with their
password and connect Google instead. Aliases, Gmail dot variations, different Google
subjects and existing accounts are not guessed to be the same identity.

For new Google-only registration, the implementation accepts verified Gmail addresses
or verified Workspace addresses whose signed hosted-domain claim matches the email
domain. Other third-party email providers require the existing password-account
connection flow. This follows Google's distinction between verified email claims
and providers for which Google is authoritative. A verified email by itself is not
used to take over an existing account. See [Google's backend authentication guidance](https://developers.google.com/identity/sign-in/web/backend-auth).

Google-only accounts receive an undisclosed random password hash; the app does not
invent or display a password users could reuse. There is no password-setting/reset
flow in this change. Account settings display the Google address recorded at connection
time. Connections cannot currently be unlinked, reassigned or replaced. Administrative
recovery and provider-email synchronization require a separate audited design.

## Verification and session security

Before rendering the chooser, the backend issues a random nonce and challenge ID.
It stores only their hashes, a hash of a separate HttpOnly browser cookie, expiry,
client ID and intent. Challenges last ten minutes, are scoped to one browser, and
are consumed once before token verification. A new attempt invalidates that browser's
older pending challenge. Expired challenges are cleaned on later starts. Challenge,
nonce, provider credential and user ID are never interchangeable.

The backend uses `google.oauth2.id_token.verify_oauth2_token` to validate the signature,
Google issuer, configured audience and timestamps against Google's certificates.
It additionally requires the saved nonce, verified email, a valid subject, correct
authorized party when present, recent issue time and finite numeric timestamps.
Only fixed Google certificate endpoints are used. Certificate requests time out after
ten seconds; provider failures return safe messages and require a fresh attempt.

Connection challenges additionally require password confirmation and the existing
authenticated session's CSRF check. Completion rechecks that exact session, its
revocation/expiry and account activity. Disabled accounts cannot use Google to bypass
account restrictions. Authenticated users cannot silently switch to another account.

Account creation/connection, audit and session issuance happen in one transaction.
Any prior app session used in completion is revoked before rotating its token and
CSRF cookie. Failed transactions roll back user/identity/session changes. Google ID
tokens are not persisted, logged or placed in browser storage. Successful completion
returns public user data and the normal app cookies, not a Google token or app bearer
token. Existing nonbrowser password-login bearer support remains unchanged.

Origin checks apply to starts and completion. The existing rate limiter allows 20
challenge starts and 20 completions per IP per 15 minutes; password-confirmed connection
starts allow 10 per app user per 15 minutes. API responses retain private/no-store and
no-referrer protections. SPA documents served by the backend/Nginx allow only origin
referrers cross-site and compatible Google popup communication. The SDK loader has a
15-second loading timeout and the Google-documented localhost referrer policy.

The Google SDK is loaded from its official URL, not bundled or self-hosted. If an
upstream deployment adds CSP/COOP restrictions, retain the allowances described in
[Google's setup reference](https://developers.google.com/identity/gsi/web/guides/get-google-api-clientid).
The nonce is supplied through the documented [Identity Services JavaScript API](https://developers.google.com/identity/gsi/web/reference/js-reference).

## APIs and implementation

All routes below use `/api/v1/auth/google`:

| Method | Path | Purpose |
| --- | --- | --- |
| GET | `/config` | Public enabled flag and public client ID only when ready |
| POST | `/challenge` | Browser-bound single-use Google-login challenge |
| POST | `/link/challenge` | Authenticated, CSRF-protected password confirmation and connection challenge |
| POST | `/complete` | Verify Google credential and establish/rotate an app session |
| GET | `/connection` | Authenticated user's connection status and email/time recorded at connection |

The credential payload contains only `challenge_id` and `credential`; clients cannot
choose a user ID, email, permissions, connection intent or destination URL. The backend
derives those from the saved intent and verified Google identity. Frontend navigation
after login goes to `/conferences`; account connections remain on `/account`.

Main files:

- `backend/app/services/google_auth.py`: verification, claims and identity resolution.
- `backend/app/api/google_auth_routes.py`: challenges, connection and cookie login APIs.
- `backend/app/auth.py`: common session issuance shared with password login.
- `backend/app/storage/migrations/007_google_auth.sql`: Google identities and temporary challenges.
- `frontend/src/components/GoogleSignIn.jsx`: official button, password confirmation and retry states.
- `frontend/src/lib/googleIdentity.js`: bounded official SDK loader.
- `frontend/src/pages/Account.jsx`: account connection screen.
- `backend/tests/test_google_auth.py`: signed-token, identity, session and attack regressions.

The Google identity table has a unique subject and unique app user ID, permitting
one Google connection per account. Foreign keys preserve account/session relationships.
Identity-update/delete triggers prevent ordinary replacement. Older schema-4/5/6
installations keep password authentication and their existing features; Google config
reports disabled and starts require explicit activation instead of creating tables.

## Database activation

The read-only preflight from `platform-v4.db` passed with no issues and zero legacy
papers requiring revision reconciliation. It created no target. The current registered
schema is 7; this supersedes the earlier pending `platform-v6.db` activation procedure.
The combined copy upgrade includes migrations 5 (formal reviews), 6 (conference intake)
and 7 (Google sign-in). Merely setting a target filename does not pin a migration version.

Read-only preparation from the repository root:

```bash
PYTHONPATH=backend python -m app.storage.migrate \
  --upgrade-from backend/data/platform-v4.db --target backend/data/platform-v7.db
```

After explicit approval, stop all application writers and retain verified database,
configuration and uploaded-file backups. The prepared copy upgrade is:

```bash
PYTHONPATH=backend python -m app.storage.migrate \
  --upgrade-from backend/data/platform-v4.db --target backend/data/platform-v7.db \
  --apply --offline
```

Verify original table values, file hashes, schema checksums, integrity and foreign keys.
Then set only `WORKFLOW_DB_PATH` to the absolute new target, configure the OAuth client
ID, and restart. Preserve the session secret and retained source database. After new
writes, rollback needs reconciliation; changing the path back alone would hide records.
The following local activation has now completed with explicit approval. Google
Cloud client registration was supplied by the user; no production deployment was
performed.

### Local activation result

The verified copy upgrade from `platform-v4.db` to `platform-v7.db` applied migrations
5–7 and preserved all 134 original application records. Seven original durable data
files remained unchanged. Integrity, foreign keys, migration checksums and every
original table value were checked before switching configuration. Configuration,
data copies and a consistent database backup are retained under
`backend/data/backups/google-auth-20261017T075318Z/` with a verification manifest.

Only `WORKFLOW_DB_PATH` changed in `backend/.env`; the user-supplied client ID,
persistent session secret, cookie settings and other configuration were preserved.
The original backend was stopped gracefully and restarted on `127.0.0.1:8000`.
Health returned HTTP 200. Both the direct backend and the frontend proxy on
`localhost:5173` returned `enabled=true` from `/api/v1/auth/google/config`.

## Validation and limits

Thirty Google-specific tests passed using real RSA-signed ID tokens, isolated local
keys, and a stub certificate transport. They cover forged signatures/algorithms,
issuer/audience/nonce/time/email checks, browser binding, replay, concurrent callbacks,
explicit linking, CSRF, session revocation, email changes/collisions, inactive users,
rate limiting, transaction rollback, network failure and older-schema compatibility.
Full regression: **338 passed, 8 skipped** (the existing external Springer fixtures
are absent). The production frontend build, complete UI harness and whitespace
checks passed. All backend/test account data was isolated under temporary paths.

The UI harness uses the real temporary backend for password login/account status and
all earlier app flows. Only its external Google chooser branch uses a stub SDK and
Google-auth API responses to check rendering, nonce configuration and failed-credential
recovery. It is not a live Google consent/browser-popup test. That final smoke test
requires your configured web client, authorized origin and approved schema activation.

Certificate fetching is bounded but has no distributed cache. Provider account unlink,
recovery/password setup, Cross Account Protection signals and durable auth-event
retention tooling are future work. Google service-account Drive integration remains
separate and retains its existing access policy.
